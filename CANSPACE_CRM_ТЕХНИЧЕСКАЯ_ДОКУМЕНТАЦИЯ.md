## 2. Общая архитектура

### 2.1 Тип приложения

Canspace — это **SPA (Single Page Application) только на фронтенде**. На данный момент не имеет собственного бэкенда. Всё состояние хранится в `localStorage` браузера через Zustand.

В проекте имеется справочная Prisma/PostgreSQL схема (`prisma/schema.prisma`), подготовленная для будущей интеграции с бэкендом, но в текущей версии она не подключена.

### 2.2 Структура папок

```
src/
├── components/
│   ├── cultivo/          → 23 компонента модуля культивации
│   ├── tabs/             → 14 основных вкладок дашборда
│   ├── ui/               → 6 переиспользуемых UI-компонентов
│   ├── agronomy/         → Банк генетики и профили сортов
│   ├── diario/           → Журнал активности
│   ├── location/         → Топология помещений/столов/уровней
│   ├── settings/         → Настройки системы
│   ├── socios/           → Управление командой/пациентами
│   ├── traceability/     → Прослеживаемость партий (LinajeDelLote)
│   └── branding/         → Логотип и брендинг
├── store/
│   ├── useCultivationStore.ts      → Основной стор культивации
│   ├── cultivationTypes.ts         → Все TypeScript-типы
│   ├── useCrmStore.ts              → Сотрудники, сток, документы
│   ├── useLocationTopologyStore.ts → Помещения и столы
│   ├── useSettingsStore.ts         → Настройки
│   ├── useSociosStore.ts           → Участники/пациенты
│   └── useStrainsStore.ts          → Банк сортов
├── lib/                  → Утилиты и хелперы (30+ файлов)
├── data/                 → Профили сортов и симптомы (статика)
└── i18n/                 → Переводы ES/RU
```

### 2.3 Хранение данных

- **Движок:** Zustand с middleware JSON-персистентности в `localStorage`
- **Ограничение:** Лимитировано хранилищем браузера (~5–10 МБ)
- **Риск:** Фотографии и изображения сохраняются как base64 (Data URLs), что может быстро переполнить хранилище при большом количестве фотозаписей
- **Без кросс-устройственной синхронизации:** данные существуют только в браузере, где они были введены

## 4. Полный цикл выращивания

Ядро системы — **модуль Культивация**, организованный как канбан из 4 этапов:

```
Проращивание → Вегетация → Цветение → Урожай
                                          ↓
                               Конвейер послеуборочной обработки
                              Сушка → Курирование → Сток
```

---

### 4.1 Этап 1: Проращивание (Прорастание / Клонирование)

**Описание:** Точка входа цикла. Представляет семена в стадии прорастания или черенки в стадии укоренения. На этом этапе единицы **ещё не имеют присвоенного браслета**.

**Данные, вводимые при создании партии/растения:**

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| Сорт (strain) | автодополнение | Да | Связан с банком генетики |
| Тип происхождения | enum | Да | `Семя` или `Черенок` |
| Тип генетики | enum | Да | `Фотопериодная` или `Автоматическая` |
| Количество | целое число | Да | ≥2 для партии, =1 для отдельного растения |
| Режим выращивания | enum | Да | `Indoor` или `Outdoor` |
| Дата посева | ГГГГ-ММ-ДД | Да | Дата начала |
| Метод прорастания | enum | Нет | Хлопковые диски / вода / торфяная таблетка / прямо в почву / другое |
| Происхождение черенка | enum | Условно | Если черенок: `Собственный` или `Внешний` |
| Материнское растение | ID | Условно | Если Собственный черенок: ID маточного растения из реестра |
| Внешний источник | текст | Условно | Если Внешний черенок: название поставщика |
| Местоположение | топология | Да | Помещение → Стол/Fixture → Уровень |

**Автоматически генерируемые ID:**
- `id`: `L{timestamp}` (партия) или `P{timestamp}` (растение)
- `sourceBatchId`: UUID исходной партии (для прослеживаемости)

**Доступные действия:**
- Редактировать запись
- Удалить запись
- Просмотр деталей (боковая панель с полной историей)
- **Пересадить в Вегетацию** → открывает TransplantModal

**События в непрерывном журнале:**
- `batch_created` (автоматически при создании)
- Чек-листы проращивания (акклиматизация, листовое опрыскивание, проверка корней)
- Записи о выбраковке сеянцев
- Произвольные заметки

---

### 4.2 Этап 2: Вегетация

**Описание:** Растения пересаживаются в зону вегетативного роста. **Именно здесь впервые присваиваются браслеты/физические ID**.

**Модальное окно пересадки (TransplantModal) — захватываемые данные:**

| Поле | Описание |
|---|---|
| Режим браслета | По ID (QR-скан) или по цвету (цветной физический браслет) |
| braceletId для каждого растения | Если режим ID: QR-скан или ручной ввод по каждому растению |
| Цвет браслета | Если режим «Цвет»: выбор цвета (красный/синий/зелёный/жёлтый/белый/чёрный) + количество живых растений |
| Потери (выбраковка) | Количество + причина: отторжение / слабые корни / плесень / не проросло / другое |
| Заметки сессии | Произвольный комментарий о пересадке |
| Новое местоположение | Помещение → Стол → Уровень в топологии |

**Индикаторы на карточке (CultivoLoteListRow):**
- Название сорта + ID партии
- Счётчик растений: активные / всего / на карантине
- Янтарное кольцо, если есть растения на карантине
- Дата начала вегетации
- Для генетики **Автоматической**: обратный отсчёт «Цветение через X дней» (расчёт: дата посева + 28 дней)
- Для генетики **Фотопериодной**: обратный отсчёт не отображается (цветение запускается сменой фотопериода)

**Доступные действия:**
- Просмотр деталей / редактирование
- Разделить партию (Split)
- Удалить партию
- **Перейти к Цветению** (основная кнопка) → открывает MoveToFlowerModal

---

### 4.3 Этап 3: Цветение

**Описание:** Репродуктивный период растения. Фиксируются подробные агрономические данные, отслеживается прогресс к уборке урожая.

**Модальное окно перехода к Цветению (MoveToFlowerModal) — захватываемые данные:**

| Поле | Описание |
|---|---|
| Выбор растений | Чекбокс по каждому растению с проверкой braceletId. Невыбранные помечаются как выбраковка |
| Дата начала цветения | ГГГГ-ММ-ДД |
| Продолжительность в неделях | **Обязательно только для фотопериодных** (напр.: 9 недель). Определяет расчётную дату уборки |
| Тип применённой обрезки | Никакая / Lollipopping / Topping / Дефолиация |
| Средняя высота | Сантиметры при входе в цветение (опционально) |
| Новое местоположение | Если переносятся в помещение для цветения |

**Индикаторы на карточке:**
- Название сорта + ID + суффикс сегмента, если партия была разделена (A, B, C...)
- Дни цветения (счётчик с `floracionStartedAt`)
- **Обратный отсчёт до уборки** (расчёт: датаНачала + недели × 7 дней)
- Опциональный суб-этап: Пред-цвет / Развитие / Созревание
- Счётчик активных/всего/карантин растений

**Технический журнал в цветении (записи дневника):**

| Тип записи | Поля |
|---|---|
| Осмотр (IPM) | Оценка здоровья 1–5, вредители (трипсы/паутинный клещ/тля), болезни (мучнистая роса/ботритис/дефицит азота), стадия трихом (прозрачные/молочные/янтарные), фото |
| Полив и питание | pH входящий, pH дренаж, EC входящий, EC дренаж, объём (л), статус промывки (да/нет), использованный рецепт |
| Климат | Температура (°C), Относительная влажность (%), VPD (кПа), CO2 (ppm), PPFD (мкмоль/м²/с), DLI |
| Обслуживание | Дефолиация, швацц, вторая сетка (SCROG), произвольные заметки |
| Фитосанитарная клиника ИИ | Диагностика по фото через Google Gemini: определение проблемы, уровень уверенности %, рекомендованное лечение |

**Доступные действия:**
- Просмотр деталей / редактирование
- Разделить партию
- Удалить партию
- **Убрать урожай** (основная кнопка) → открывает HarvestModal

---

### 4.4 Этап 4: Урожай

**Описание:** Акт срезки. Растения перемещаются из канбана цветения в канбан урожая. Одновременно создаётся запись `HarvestBatch` в статусе DRYING для запуска конвейера послеуборочной обработки.

**Модальное окно Урожая (HarvestModal) — подтверждение:**
- Название сорта
- Количество растений (отдельное или вся партия)
- Местоположение источника
- Кнопка подтверждения

**При подтверждении урожая:**
1. Карточки растений перемещаются из `floracion[]` в `cosecha[]` в канбане
2. Создаётся запись `HarvestBatch` с `postHarvestStatus: 'DRYING'`
3. Записывается `cosechaStartedAt` (ISO-временная метка)
4. В непрерывный журнал добавляется событие `moved_to_cosecha`

**Вкладка «Урожай» отображает два раздела:**
1. **Карточки убранных растений** — история того, какие растения были срезаны и когда
2. **Конвейер послеуборочной обработки** — управление материалом после срезки (см. раздел 10)

## 5. Система идентификации: браслеты, QR-коды и ID растений

### 5.1 Три уровня идентификации

```
┌─────────────────────────────────────────────────────────────────┐
│  УРОВЕНЬ 1: id                                                  │
│  Технический внутренний ID. Формат: L{timestamp} (партия)      │
│  / P{ts} (растение). Генерируется автоматически.               │
│  Не виден оператору.                                            │
├─────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 2: sourceBatchId                                       │
│  UUID исходной партии. Связывает все единицы одной посевной     │
│  партии, даже после разделений.                                 │
├─────────────────────────────────────────────────────────────────┤
│  УРОВЕНЬ 3: braceletId                                          │
│  Физический браслет. Присваивается при Вегетации. То, что      │
│  оператор видит и сканирует в теплице.                          │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 Режим ID (QR / числовой код)

- Каждое растение получает уникальный буквенно-цифровой код (напечатан на QR или написан на браслете)
- Ввод: камера (OCR с Tesseract.js) или ручной ввод с клавиатуры
- Автоматическая нормализация: удаляется `#`, обрезаются пробелы, преобразуется в нижний регистр для дедупликации
- Проверка уникальности: система отклоняет дублирующиеся ID в одной партии
- Система может верифицировать braceletId при переводе растений на цветение (подтверждение идентичности)

### 5.3 Режим «Цвет» (цветной физический браслет)

Предназначен для операций, использующих цветные стандартные браслеты вместо индивидуальных QR-кодов.

| Доступный цвет | Пример генерируемого ID |
|---|---|
| Красный | `Red-01`, `Red-02`, ... |
| Синий | `Blue-01`, `Blue-02`, ... |
| Зелёный | `Green-01`, `Green-02`, ... |
| Жёлтый | `Yellow-01`, `Yellow-02`, ... |
| Белый | `White-01`, `White-02`, ... |
| Чёрный | `Black-01`, `Black-02`, ... |

Пользователь вводит количество живых растений, и система последовательно генерирует ID.

### 5.4 OCR-сканер (Инструменты)

Модуль **Инструменты** включает сканер браслетов через камеру устройства:
- Движок: Tesseract.js v7 (OCR в браузере, без бэкенда)
- Распознаёт числовые и буквенно-цифровые печатные коды
- Позволяет ручную коррекцию перед подтверждением
- Не требует специального оборудования (работает с камерой смартфона/планшета)

## 6. Система материнского растения и клонирования

### 6.1 Назначение материнского растения

- Любое растение из реестра может быть помечено как `isMotherStock: true`
- Маточные растения, как правило, расположены в специально выделенном помещении (не производственном)
- Отображаются в специальном поиске (MotherPlantSearchSelect) при создании новых черенков

### 6.2 Типы происхождения черенка

| Тип | Поле | Описание |
|---|---|---|
| **Собственный черенок** | `cloneOrigin: 'propio'` | Черенок взят с материнского растения, зарегистрированного в системе |
| | `motherPlantId` | ID материнского растения-источника |
| **Внешний черенок** | `cloneOrigin: 'externo'` | Черенок приобретён у внешнего поставщика |
| | `cloneExternalSource` | Название/ссылка на поставщика (произвольный текст) |

### 6.3 Генетическая прослеживаемость

| Поле | Описание |
|---|---|
| `cloneGeneration` | Поколение черенка: F1, Ген 2, Ген 3... |
| `rootingHormone` | Использованный корнеобразующий гормон |
| `motherPlantId` | Прямая ссылка на маточное растение в реестре |
| `sourceBatchId` | Партия-источник данной серии черенков |

Полная цепочка прослеживаемости позволяет отследить грамм готовой продукции до исходного черенка и до материнского растения, которое его произвело.

## 7. Разделение партий (Split)

### 7.1 Условия применения

- Только на этапах Вегетация или Цветение
- Требуется минимум 2 активных растения в партии
- Можно делить столько раз, сколько необходимо

### 7.2 Данные в модальном окне разделения

| Поле | Валидация |
|---|---|
| Количество растений для перевода | Мин: 1 / Макс: кол-во_активных - 1 |
| Новое местоположение (помещение → стол → уровень) | Обязательное |

### 7.3 Что происходит при разделении

1. N выбранных растений получают **новый `sourceBatchId`** (новый UUID)
2. Исходные растения сохраняют свои `braceletId` и технический `id` — физический тег не изменяется
3. Назначается **суффикс сегмента** (`lotSegmentSuffix`): A, B, C, D...
   - Исходная партия остаётся как «Сорт»
   - Новый сегмент отображается как «Сорт — B»
4. Событие записывается в непрерывный журнал:
   ```
   systemKey: 'lote_split'
   movedCount: N
   newBatchId: '...'
   fromBatchId: '...'
   locationLabel: 'Помещение X > Стол Y'
   ```
5. Оба сегмента полностью независимы: могут продвигаться по этапам, убираться и классифицироваться отдельно

### 7.4 Прослеживаемость после разделения

| Поле | Функция |
|---|---|
| `sourceBatchId` | ID текущего сегмента, к которому принадлежит растение |
| `splitFromSourceBatchId` | ID сегмента-источника (если растение было разделено) |
| `lotSegmentSuffix` | Буква сегмента (A/B/C) |

## 9. Непрерывный журнал (Audit Trail)

Каждая партия/растение имеет **хронологический неизменяемый журнал** (`propagacionLog`), который формируется с момента создания до уборки урожая. Функционирует как цифровой полевой журнал.

### 9.1 Типы записей

| Тип (`kind`) | Описание |
|---|---|
| `system` | Автоматические события системы (создание, смена этапа, разделения) |
| `note` | Произвольная заметка оператора |
| `measurement` | Ручное измерение (pH, EC, температура) |
| `diario_riego_nutricion` | Запись полива: рецепт, объём, pH/EC вход-дренаж, промывка |
| `diario_inspeccion` | IPM-осмотр: оценка здоровья, вредители, болезни, трихомы, фото |
| `diario_clima` | Климатическая запись: темп, ОВ, VPD, CO2, PPFD, DLI |
| `diario_mantenimiento` | Работы: дефолиация, швацц, SCROG, заметки |
| `diario_propagacion_checklist` | Чек-лист проращивания: акклиматизация, листовое опрыскивание, корни |
| `diario_descarte` | Выбраковка сеянцев: количество + причина |
| `diario_altura_canopy` | Высота полога в сантиметрах |
| `diario_baja_planta` | Официальное списание растения: акт, ID, причина, вес, метод уничтожения |
| `diario_cuarentena` | Начало карантина: поражённые растения, причина, местоположение |
| `diario_reubicacion` | Перемещение растений: ID, количество, новое местоположение |

### 9.2 Автоматические системные события

| `systemKey` | Когда срабатывает |
|---|---|
| `batch_created` | При создании партии/растения в проращивании |
| `moved_to_vegetacion` | При подтверждении пересадки в вегетацию |
| `moved_to_floracion` | При подтверждении перехода к цветению |
| `moved_to_cosecha` | При подтверждении уборки урожая |
| `lote_split` | При разделении партии |

### 9.3 Структура записи журнала

```typescript
{
  id: string,               // Уникальный ID записи
  at: string,               // ISO-временная метка (напр.: "2026-03-15T14:32:01.000Z")
  kind: PropagacionLogKind, // Тип (см. таблицу выше)
  author?: string,          // Пользователь, создавший запись
  text?: string,            // Произвольная заметка

  // Дополнительные поля по типу:
  ph?: number,
  ec?: number,
  tempC?: number,
  systemKey?: string,       // Только для kind: 'system'

  // Структурированный payload по типу kind:
  diarioRiegoNutricion?: { recipeLabel, volumeValue, volumeUnit, inletPh, inletEc, drainPh, drainEc, flushStarted },
  diarioInspeccion?: { healthScore, pests[], diseases[], trichomeStage, photoDataUrl, notes },
  diarioClima?: { tempC, rhPct, vpdKpa, co2Ppm, ppfd, dli },
  // ...и т.д.
}
```

## 10. Конвейер послеуборочной обработки

Интегрирован непосредственно внутрь вкладки **Урожай** модуля Культивация.

Конвейер управляет объектами `HarvestBatch` (отличными от карточек растений). Каждый акт уборки автоматически создаёт `HarvestBatch` в статусе DRYING.

### 10.1 Три колонки конвейера

```
┌──────────────┐     ┌──────────────┐     ┌──────────────────┐
│   СУШКА      │────▶│  КЮРИНГ      │────▶│  ФИНАЛЬНЫЙ СТОК  │
│   (DRYING)   │     │  (CURING)    │     │  (STOCK)         │
└──────────────┘     └──────────────┘     └──────────────────┘
```

### 10.2 Колонка 1: СУШКА (DRYING)

**Отображаемая информация:**
- Название сорта
- Дней с момента срезки (расчёт от `harvestDate`)
- Дата срезки (ГГГГ-ММ-ДД)
- Помещение сушки (roomLabel + tableLabel)
- Редактируемое поле: **Свежий вес** (граммы)

**Доступное действие:** «Перейти к Кюрингу»

**Модальное окно «Перейти к Кюрингу» захватывает:**
| Поле | Валидация |
|---|---|
| Общий сухой вес (г) | Обязательное, должно быть > 0. Если внесён свежий вес — не может его превышать |
| Потери от тримминга (г) | Опционально, не может быть отрицательным |

---

### 10.3 Колонка 2: КЮРИНГ (CURING)

**Отображаемая информация:**
- Название сорта
- Зафиксированный сухой вес
- Потери от тримминга (если есть)
- Дней кюринга (расчёт от `curingStartedAt`)

**Доступное действие:** «Зарегистрировать сток»

**Модальное окно «Зарегистрировать сток» захватывает:**
| Поле | Валидация |
|---|---|
| Граммы Premium | Число ≥ 0 |
| Граммы Popcorn | Число ≥ 0 |
| Граммы Биомасса | Число ≥ 0 |
| Местоположение хранилища | Выбор существующего помещения ИЛИ произвольный текст. Обязательное |

Валидация: сумма Premium + Popcorn + Биомасса должна быть > 0 и ≤ зафиксированному сухому весу.

---

### 10.4 Колонка 3: ФИНАЛЬНЫЙ СТОК (STOCK)

**Отображаемая информация:**
- Название сорта
- Местоположение в хранилище (vault)
- Разбивка в граммах:
  - Premium (г)
  - Popcorn (г)
  - Биомасса (г)
  - **Всего классифицировано** (г)

**Действия:**
- Просмотр полной прослеживаемости (LinajeDelLoteModal — показывает цепочку от семени до продукта)

---

### 10.5 Структура объекта HarvestBatch

```typescript
HarvestBatch {
  id: string,
  strain: string,
  plantIds: string[],          // ID убранных PlantCardItem
  plantCount: number,
  harvestDate: string,         // ГГГГ-ММ-ДД
  postHarvestStatus: 'DRYING' | 'CURING' | 'STOCK',

  // Веса
  wetWeight: number | null,    // Свежий вес при срезке (г)
  dryWeight: number | null,    // Сухой вес после сушки (г)
  trimWasteWeight: number | null, // Потери от тримминга (г)

  // Кюринг
  curingStartedAt?: string,    // ISO-временная метка начала кюринга

  // Классификация стока
  stockGradePremiumG: number | null,
  stockGradePopcornG: number | null,
  stockGradeBiomassG: number | null,

  // Местоположение
  roomId: string,
  tableId: string,
  roomLabel: string,
  tableLabel: string,
  vaultLocationLabel?: string, // Финальное местоположение в хранилище

  archived: boolean,
  createdAt: string,
}
```

## 12. Остальные модули дашборда

### 12.1 Банк генетики (AgronomyTab)

Библиотека сортов с полными профилями:
- Название, бридер, тип (фотопериодная/автоматическая/CBD)
- Процентное содержание: THC, CBD, Sativa, Indica, Ruderalis
- Ароматы, эффекты, лечебные свойства, основные терпены
- Подробное описание и заметки по выращиванию
- Интегрируется с полем Сорт в форме создания партий (автодополнение)

### 12.2 Сток / Инвентарь

- Управление готовой продукцией
- Цены в ARS (наличные / перевод) и USDT
- Привязка к HarvestBatch (отпуск из убранных партий)
- Ручная корректировка стока
- Обработчик события: `inventory:restore` для возврата граммов в HarvestBatch при отменённой продаже

### 12.3 Участники (Соcios)

- Управление членами команды и/или пациентами REPROCANN
- Фотографии профиля (base64 в localStorage)
- Регистрация лицензий (REPROCANN Data URL)
- Внутренние уведомления системы

### 12.4 Топология помещений (Настройки > Компания)

- Настройка помещений учреждения
- Иерархия: Помещение → Стол/Fixture → Уровень
- Типы помещений: производство / карантин / сушка / маточные
- Карантинные и сушильные помещения исключаются из формы создания партий
- Используется во всех модулях культивации для назначения физических местоположений

### 12.5 Инструменты (ToolsTab)

- **OCR-сканер браслетов**: считывание braceletId через камеру (Tesseract.js)
- Полезен для операторов, которым нужно идентифицировать партии в теплице

### 12.6 Прослеживаемость (LinajeDelLoteModal)

- Доступно из любого `HarvestBatch` в колонке Сток
- Показывает полную цепочку: семя/мать → проращивание → вегетация → цветение → урожай → сток
- Включает даты, счётчики, ID и переходы между этапами
- Разработано для поддержки регуляторных аудитов

| **Нет реальной базы данных** | Данные пропадают при очистке браузера | Высокий |
| **Нет ролей пользователей** | Нет разграничения: администратор / оператор / аудитор | Средний |
| **Нет экспортируемых отчётов** | Невозможно экспортировать в PDF/Excel для аудитов | Средний |

### 14.3 Архитектура подготовлена к бэкенду

Проект включает `prisma/schema.prisma` со схемой PostgreSQL, уже разработанной для помещений, fixtures, уровней и растений. Будущая интеграция с бэкендом потребует:

1. Реализовать REST API или tRPC (Node.js / Express / Fastify)
2. Мигрировать сторы Zustand для получения данных из API вместо чтения из localStorage
3. Реализовать аутентификацию (JWT или сессии)
4. Перенести хранилище изображений во внешний сервис (S3, Cloudinary и т.д.)
5. Включить прокси для сторонних API с ограничениями CORS (OpenAI, Claude)
